Rampart

A self-hosted, open-core firewall and attack-analytics platform. This page is a single-page reference — every section below links out to the fuller Markdown doc it's condensed from, so nothing here is the only copy of the truth.

Overview #

Rampart sits in front of your application as a reverse proxy and blocks network-, application-, and API-layer attacks in one place, then gives you a single dashboard to see what was blocked and why — instead of stitching together nginx + ModSecurity + fail2ban + a log pipeline + a dashboard.

LayerWhat it doesStatus
NetworkReverse proxy, IP allow/deny, rate limitingdone
Application (WAF)Coraza + OWASP Core Rule Set, custom SecLang rulesdone
API / mobile-backendCredential-stuffing detection, JSON Schema request validationdone
AnalyticsLive dashboard, offline triage tool (rampart-analyze)done
OIDCDashboard login + API RBAC against an existing IdPdone
Cloud-nativeDocker, Helm, Terraform (AWS ECS Fargate)done
Hosted ConsolePaid tier — multi-node, longer retention, threat intelnot started

Quick start #

go build -o bin/rampart ./cmd/rampart
cp configs/rampart.example.yaml configs/rampart.yaml
# edit configs/rampart.yaml: set upstream to the app you're protecting
./bin/rampart -config configs/rampart.yaml

Rampart listens on listen (default :8080) and proxies allowed traffic to upstream. Every block decision is written as a JSON line to logging.events_path.

Or: zero-setup Docker demo

docker compose up
# attack it at http://localhost:8080, dashboard at http://localhost:9090

Runs Rampart in front of a bundled OWASP Juice Shop instance. See docs/DEPLOYMENT.md for Helm and Terraform options.

Detection layers #

Four independent layers run in front of every request; a request only needs to trip one to get blocked. Full detail and real examples: docs/DETECTION.md.

WAF — cumulative anomaly score

Coraza + OWASP CRS. Each matched rule adds points to a request's anomaly score; only crossing a threshold blocks it — so one borderline signal doesn't block legitimate traffic, but several stacking up does.

PayloadResult
1' OR '1'='1403, anomaly score 20
<script>alert(1)</script>403, anomaly score 15

API-abuse — behavior over time

Counts failure responses per IP against a configured endpoint over a sliding window; no request content is inspected.

api_abuse:
  enabled: true
  rules:
    - name: "login-brute-force"
      methods: ["POST"]
      path_prefix: "/rest/user/login"
      failure_status_codes: [401]
      max_failures: 5
      window: 1m
      block_duration: 5m

Schema validation — shape, not signature

Rejects a request body that doesn't match a declared JSON Schema for the route — catches mass-assignment and structurally-wrong requests a signature-based WAF isn't designed to flag.

Rate limiting — pure volume

Per-IP requests/sec, burst allowance, and max concurrent in-flight requests. Catches flood-shaped traffic with nothing content-wise to flag.

OIDC integration #

Rampart integrates with an existing identity provider (Keycloak, Auth0, Okta, ...) rather than becoming one — no user store, no login UI, no token issuance. Two independent features:

  • Dashboard login (oidc.dashboard_auth) — Authorization Code + PKCE, required to view the dashboard.
  • API RBAC (oidc.api_rbac) — validates access tokens on proxied requests, enforces per-route roles.
oidc:
  enabled: true
  issuer_url: "https://keycloak.example.com/realms/myrealm"
  api_rbac:
    enabled: true
    rules:
      - path_prefix: "/admin"
        required_roles: ["admin"]
      - path_prefix: "/api"
        required_roles: []   # any valid token
Verified against a real Keycloak instance, not mocks — including finding that roles live on the access token, not the ID token, on stock Keycloak. Full walkthrough and the Keycloak-specific gotchas: docs/OIDC.md.

Deployment #

Docker

docker build -t rampart .
docker run -d -p 8080:8080 -p 127.0.0.1:9090:9090 \
  -v $(pwd)/configs/rampart.yaml:/app/configs/rampart.yaml:ro \
  -v rampart-data:/data \
  rampart

Distroless, non-root (UID 65532). /app read-only, /data the only writable path.

Kubernetes (Helm)

helm install my-rampart ./deploy/helm/rampart --set upstream=http://myapp:8080

Standalone, sidecar, or ingress-exposed patterns — see deploy/helm/rampart/README.md. helm lint/helm template verified; not yet run against a live cluster.

AWS (Terraform, ECS Fargate)

module "rampart" {
  source = "./deploy/terraform/aws-ecs-fargate"
}

Written against the documented provider schema; not yet run through terraform validate in this environment.

The dashboard has no authentication of its own. Every deployment path here defaults to keeping it off a public interface — widening that requires either OIDC dashboard auth or an authenticating proxy in front.

rampart-analyze #

A separate binary — no dependency in the core proxy or its build — that reads a window of the block-event log and produces a Markdown triage report: top attackers, top block reasons, IPs that triggered more than one detection layer, and traffic bursts.

go build -o bin/rampart-analyze ./cmd/rampart-analyze
./bin/rampart-analyze -events rampart-events.jsonl -since 168h -out report.md
Scope, stated plainly: every event is a block decision only — no payload, no record of allowed traffic. This tool can triage what's already caught; it cannot find coverage gaps or draft new rules from data that isn't there. Full reasoning: docs/ANALYZE.md.

Optional -narrate flag adds a plain-English summary via the Anthropic API (ANTHROPIC_API_KEY), skipped automatically if unset — the tables-only report always works without one.

Benchmarks #

Measured with GoTestWAF, WAF layer in isolation (rate limiting/IP filtering disabled for a clean measurement). Full methodology and reproduction steps: benchmarks/RESULTS.md.

OverallTrue-positiveFalse-positive rate
ModSecurity standalone (bare, PL1)63.27%48.20%9.22%
Rampart baseline (Coraza, no custom rules)63.12%47.63%9.22%
Rampart + base64 anti-evasion rule65.25%55.93%9.22%

Rampart's baseline matching ModSecurity within noise confirms Coraza's reimplementation is faithful to the original engine, not a degraded copy. The gap to Rampart's final number is real, measured value from one targeted custom rule closing a base64-encoding evasion gap both engines share by default — with the false-positive rate holding exactly steady while it closed.

This isolates the WAF layer only: ModSecurity's number is its entire product at this layer, while Rampart's is one layer of a product that also ships credential-stuffing detection, schema validation, rate limiting, and a live dashboard.

Public demo tooling #

Built and tested, not currently deployed. A separate config (configs/rampart.demo-public.yaml) and standalone compose file (docker-compose.public-demo.yml) expose the dashboard publicly with a tightened rate limit and a configurable notice banner (dashboard.public_notice) — for a Juice-Shop-only demo, never for a deployment protecting a real application.

Held off on actually deploying this publicly: it would be the first time this project has run on the open internet, with no monitoring in place yet. The code is ready when the decision is made to go live.
